# tools/gx/ and the certificates gcert1-p11-pr193.json.gz and gcert1-e8-r783.json.gz: where they come from

Everything in this directory is Python 3 (standard library only). No Lean is run by these scripts.
"The outside repository" means github.com/CrocSwap/integer-mult-bounds (Apache-2.0, `LICENSE` and `NOTICE`
of that repository; `NOTICE`: "A sharper exponent for integer multiplication, Copyright 2026 Douglas Colkitt").

## The scripts (this project)

| file | what it is |
|---|---|
| `gxcore.py` | loads a certificate of format gcert/1, brings it to normal form, and is a Python mirror of both Lean checks (labels and scalars); cut points and label data for the generator |
| `gxunit.py` | split plan of the kernel evaluations, the unit of the word, expected exponents |
| `gxbind.py` | the texts of the generated Lean modules (check, histogram, price, certificate and final modules) |
| `gxgen.py` | certificate -> Lean data modules and one module per kernel evaluation |
| `gxrate.py` | rate lemmas, unit price list, final theorem modules, comparator challenge / solution / configuration |
| `gxdry.py`, `gxmut.py` | dry run (mirror, sizes, plan, exponents); mutants that the mirror must reject |
| `gxconv.py` | converts the earlier format gcert/0 to gcert/1 when a step scales its target (the in-place pair step of #193) |
| `gsmirror.py` | a second, separately written Python mirror of the scalar check `GS.scalCheck` / `GS.yCheck`; `gxbind.py` calls it for the check parameters |
| `gx.py`, `gxrun.py` | the reference checker of the format (`gx.check1`: labels and exact scalar identity) and its command line |
| `gxpaths.py`, `regen_check.py`, `refcheck.py` | written for this repository: relative paths; regenerate and compare; `gx.check1` on a gcert/1 file |
| `regen_check_e8.py` | written for the fourth revision (2026-10-10): checks the sha256 of the certificate of the fourth result and runs `regen_check.py`, unchanged, with its three arguments |

The scripts of this directory, except `regen_check_e8.py`, are the working copies with path edits only (absolute paths of my machine replaced through
`gxpaths.py`; templates read from `tools/gen/templates/`; `foldlib.py` / `foldgen.py` taken from `tools/gen/`).
The sentences "Generated by checks/..." that the generators print into Lean files name the scripts by their
working paths; they are kept so that the generated modules come out byte for byte.
No script of the outside repository is included in this directory, imported or executed.

`tools/rebuild/` (13 files) is different. It holds the scripts that rebuild the first certificate below,
`gcert1-p11-pr193.json.gz`, from data files of the outside repository ("Run the rebuild yourself", below).

- These scripts import and execute no outside script either.
- None of them is an outside script unchanged.
- Six of them are adapted from scripts of the outside repository, which were read as text. Each of the six
  says so in its first lines, and `NOTICE`, section 6, names the outside files and their authors.

## The certificate `tools/certificate/gcert1-p11-pr193.json.gz`

sha256 of the file: `15251deb0c11e0504d7b297c9786818888a93f08b92b03c6c122784b70488633`
(gzip stores a time stamp; sha256 of the uncompressed JSON: `c64d2a95431c3cf24452de7391cce780bd71521da44ce23923ebb235f6c7962c`).

It is ONE explicit program (numbered registers, every addition, every frame) for the helper circuit at
h = 22: 1,320 ports, 9,412 slots, 262,944 unit moves. **The design of that circuit is not this project's.** It is the
"paired-cube" circuit of the outside repository as of pull request #193 (which builds on #191, #184, #168 and #144).
The outside repository publishes the design as generator scripts, frozen data files and a ledger; it has no file
of this kind. This project made this file in three steps. It

1. loaded the following files of the outside repository **as data** (JSON; nothing was executed):
   - at pull request #168, commit `4a3c769e5c5430e7114c4d3e099ff34664677f17`:
     `references/paired-cube/sources/local_L1.json`,
     `references/paired-cube/sources/tmod_TE_TD_TB3_1_1_4_full_6.0617964e-4.json`,
     `references/paired-cube/sources/pmod_J0_full_6.0666810e-4.json`,
     `references/paired-cube/sources/qmod_climb3u_best.json` (the local modules),
     `references/paired-cube/selected-module/matching-arcs.json` (carrier arcs),
     `references/paired-cube/physical/frames.json` (moved frames);
   - at pull request #193, commit `187e1010ac8b259af8e9b5166f68b64bc27b4b47`:
     `research/source-assisted-v4/data/physical-pairs.json` (the hand-over pairs);
   - for comparison only, at the same commit of #168:
     `references/paired-cube/selected-module/SOURCE.json` (the graph hash that the outside repository records),
     `certificates/paired-cube-complex-input.json` (its record of the counts of the #168 word).
     The rebuild prints whether its graph and its counts agree with them. Nothing in the certificate is taken
     from them;
2. rebuilt the circuit from them step by step. The scripts that did this are now in `tools/rebuild/`, in a
   tidied form. Six of them are adapted from the outside scripts, which were read as text and never run
   (`NOTICE`, section 6). The result was then checked exactly, in two ways: every published count was
   reproduced, and the scalar identity was checked as an identity of linear maps with arbitrary contents of
   the helper registers. The scripts of `tools/rebuild/` make neither check: they print the counts and do
   not compare them, and the exact replay is a program that is not in this repository ("What is not here",
   below);
3. converted it to gcert/1 with `gxconv.py` (tested by `gx.check1`).

The scripts that do step 1 and the rebuilding of step 2 are in `tools/rebuild/`. They were added in the
fourth revision, after issue #1 of this repository said that its author could not run the rebuild without
them. Of the thirteen files:

- Ten are the working scripts that made the certificate, tidied. The paths are relative now. Most of the
  parts that this certificate never used are taken out. Comments were reworded. The notices of the outside
  scripts they follow were added. `aligned.py` can read another file of hand-over pairs ("Another file of
  hand-over pairs", below).
- Three are new: `rebuild.py`, `fetch_inputs.py`, `rbpaths.py`.

Two things are not in this repository:

- The two programs that made the exact checks of step 2 are NOT in this repository ("What is not here",
  below).
- The outside files are not part of this repository either. `tools/rebuild/fetch_inputs.py` fetches them
  from the outside repository at the two commits above and checks the sha256 of each. Both commits are heads
  of pull requests that were open and not merged on the day of the fourth revision ("Sources and dates", at
  the end of this file); they are not on the main branch of the outside repository. The sha256 values fix
  the content of the files, not that they stay available.

What this repository proves about the file does not depend on how it was made: the Lean kernel checks the
generated modules (labels, scalar identity, price), and `regen_check.py` shows that those modules are exactly
what `gxgen.py` / `gxrate.py` produce from this file.

## Run the rebuild yourself

Two commands fetch the outside data files and rebuild the certificate `gcert1-p11-pr193.json.gz` from them:

    python3 -I -B tools/rebuild/fetch_inputs.py <inputs>
    python3 -I -B tools/rebuild/rebuild.py <inputs>

`<inputs>` is a directory of your choice.

- The first command needs the network. It sends nine plain HTTPS GET requests to raw.githubusercontent.com,
  one for each outside file at its commit (830,004 bytes in all). It writes a file only if its sha256 is the
  expected one.
- The second command checks the nine sha256 again and runs the rebuild in a temporary directory. It prints
  the sha256 of the uncompressed certificate next to the published value.

Expected last line, exit code 0:

    RESULT: REPRODUCED (the uncompressed content is that of the published certificate)

Compare the uncompressed content, not the `.gz` file: gzip stores a time stamp, so the `.gz` file has another
sha256 on every run. `out=<file>` keeps the rebuilt certificate; `--keep <dir>` keeps the work directory. To
compare by hand:

    gzip -dc <file> | shasum -a 256      # c64d2a95431c3cf24452de7391cce780bd71521da44ce23923ebb235f6c7962c

On Linux, use `sha256sum` in place of `shasum -a 256`.

No program of the outside repository is run or imported. The nine files are JSON and are loaded as data. In
the table, "#168" and "#193" are the two pull requests of the outside repository whose commits are given in
the section above:

| file of the outside repository | at | what it is used for |
|---|---|---|
| `references/paired-cube/sources/local_L1.json` | #168 | the local circuit of a cube |
| `references/paired-cube/sources/tmod_TE_TD_TB3_1_1_4_full_6.0617964e-4.json` | #168 | triple module |
| `references/paired-cube/sources/pmod_J0_full_6.0666810e-4.json` | #168 | pair module |
| `references/paired-cube/sources/qmod_climb3u_best.json` | #168 | all-but-one module |
| `references/paired-cube/selected-module/matching-arcs.json` | #168 | carrier arcs |
| `references/paired-cube/physical/frames.json` | #168 | moved frames |
| `research/source-assisted-v4/data/physical-pairs.json` | #193 | the hand-over pairs |
| `references/paired-cube/selected-module/SOURCE.json` | #168 | comparison only: the graph hash recorded there |
| `certificates/paired-cube-complex-input.json` | #168 | comparison only: the counts of the #168 word recorded there |

`tools/rebuild/rbpaths.py` has the size and the sha256 of each, and of one optional tenth file (next section).

The scripts of the rebuild. The numbers 1 to 6 are its six steps, in order:

| file | what it does |
|---|---|
| `rebuild.py` | checks the inputs, runs the six steps below as separate processes, compares the result |
| `fetch_inputs.py`, `rbpaths.py` | fetch and check the outside files; the list of the files with their sha256 |
| `build.py` | 1: the helper word of #168 from the modules and the carrier arcs; prints the comparison with the outside records |
| `aligned.py` | 2: the aligned word of #193: arcs and frames carried over from step 1, hand-over pairs loaded |
| `rewrite.py` | 3: the 1,980 in-place pair steps; one explicit gate list |
| `phys.py` | 4: the frames of every register, the block counts, the number of unit moves |
| `emit.py` | 5: the circuit as a file of format gcert/0 |
| `gxconv.py` (in this directory) | 6: gcert/0 to gcert/1, tested by `gx.check1` before the file is written |
| `graphgen.py`, `modules.py`, `compile.py`, `stage.py`, `f2.py` | used by steps 1 to 5 |

On the Mac on which this project was made (macOS, Python 3.9.6), the rebuild took 70 to 95 seconds and about
0.6 GB of memory. The scripts need
Python 3.9 at least, because `gx.py` uses `math.lcm`. They have not been run on another system or with
another Python version.

What is not here. Before the conversion of step 6, the intermediate word (the circuit as the earlier steps
leave it) was checked with two more programs: an exact symbolic replay, and a checker of the gcert/0 format.
**These two programs are not in this repository.** The check of the result that is in this repository is
`gx.check1`: `gxconv.py` runs it before it writes the file, and `refcheck.py` runs it on the file. The
rebuild prints the counts of the word (9,412 helper arrays, 12,052 arrays per vertex, rank mass 794,112). It
does not itself compare them with the record of #193.

## Another file of hand-over pairs

The rebuild can read another file of hand-over pairs in place of the file of #193. The other eight inputs
stay as they are.

    python3 -I -B tools/rebuild/fetch_inputs.py <inputs> pr233
    python3 -I -B tools/rebuild/rebuild.py <inputs> name=pr233 out=<file> \
        pairs=<inputs>/pr233/research/source-assisted-v4-layer/witness/physical-pairs.json

The new arguments:

- `pr233`, in the first command, fetches one more file: the pairs file of pull request #233 of the outside
  repository, at commit `109a857a329d18ed5552d5573f17ddfa886ae57f` (44,022 bytes, sha256
  `e6409fffbf5f3b1ac6434acf2e426503de3a8a18537b8fee761fc4fc931fb896`). That commit, like the two others, is
  the head of a pull request that was open and not merged on the day of the fourth revision ("Sources and
  dates").
- `pairs=` may name any file of the same form, `{"pairs": [[donor, recipient, operation index or null], ...]}`.
  Its numbers are roles and operations of the aligned word of step 2 (15,682 roles, 36,931 operations).
- `name=` replaces `pr193` in the names of the steps and goes into the certificate. The name `pr193` is
  refused, so that a certificate made from other pairs cannot carry the published name.

Expected last line with the file of #233, exit code 0:

    RESULT: BUILT with another pairs file, name pr233xword (accepted by gx.check1 in step 6)

Three lines to look at the result:

    gzip -dc <file> | shasum -a 256      # e237c947bdd14ed9d41fa350cb9b5a9be76997af6188e3b55342a50966655176
    python3 -B tools/gx/refcheck.py <file>   # ACCEPTED by gx.check1: h=22 v=1320 R=9412 N=262944 ...
    python3 -B tools/gx/gxdry.py <file>      # ... 10 decimals, fill 1 - 2^-40: whole-block 7547361 ...

What is checked of a pairs file:

- Step 2 checks its form and its ranges: a list of triples under the key `pairs`, every role and operation
  index inside the aligned word, every recipient a gauged role, no role in two entries.
- Whether the hand-overs are legal is decided later, in three places. Step 3 stops at a pair that names a
  role or an operation that it removes. In the frame scan of step 4, every register must climb through
  nested frames. `gx.check1` in step 6 checks the labels and the exact scalar identity of the finished
  circuit.

A file that fails one of these stops the rebuild with exit code 1, and no certificate is written.

What is not checked: whether the pairs are a good choice, and whose file it is. The script prints the sha256
of the pairs file it read and says whether it is the file listed in `rbpaths.py`.

What comes out. The certificate for the pairs of #233 is not part of this repository, and no theorem here
uses it. 7547361 is the price that `gxdry.py` computes for it in Python: a saving of 7.547361e-4, not checked
by Lean. The figure of this repository's second result, 7474547 (a saving of 7.474547e-4), is the one that
Lean checks. This repository does not contain Lean modules for the
other certificate. Chafik Boukhalfa's own pull request #2 of this repository has the same figure as a Lean
theorem, for a certificate of his own making. The agents built that pull request on a Linux machine on
10 October 2026, and every Lean module that it adds compiled (README, "Whose circuit this is").

## The certificate `tools/certificate/gcert1-e8-r783.json.gz` (fourth result)

sha256 of the file: `4b92f00fc7454b9b15e6d71a3b05062792eacca0a0ca4efee46f87827d57c8aa`
(sha256 of the uncompressed JSON: `3594f19c4d01cf11fb930c5c61baeed399620acbc5b94096b16bcacb23997dd3`).

This file is the certificate of the fourth result: the data file from which the generated Lean modules of
that result are written. Like the certificate above, it is ONE explicit program in the format gcert/1. Its helper
circuit is at h = 9: 120 ports, 783 slots, 9,039 unit moves.

**The design of this circuit is this project's.** The agents (the team of AI agents that the README
describes) found it by computer search. The search programs are in `tools/e8/`, and
`notes/how-the-e8-unit-was-found.md` tells how. No data file of the outside repository was loaded to make
it, and it is not the circuit of the certificate above.

Three devices in the circuit were published by others, in pull requests to the outside repository:

- the in-place pair: icekylinx;
- the re-use of finished helpers with a compensating read: jamesyc and eumemic;
- the late pairing rule: Chafik Boukhalfa (the account chafreaky), there and in pull request #2 of this
  repository.

`NOTICE`, section 8, and the README give the credit. The pull-request numbers and the date of the search are
in "Sources and dates" at the end of this file.

How it was made, in short:

1. The 120 ports are the words of 9 bits with three ones or with seven ones.
2. An integer programme, solved with HiGHS through SciPy, picks a hierarchy of shared sums from a pool of
   1,470 candidate sums.
3. A chain of passes turns the hierarchy into a certificate: a compiler, the re-use of finished helpers,
   sources read directly, totals built on used helpers, and a re-scheduler of frames and gates.

In `tools/e8/` only the solver stage (`run.py --solve`) needs NumPy and SciPy; the rest, like `tools/gx/`,
needs the standard library only. The command `python3 -B tools/e8/run.py` makes this certificate again from the
recorded hierarchy. Its last lines begin with `RESULT: REPRODUCED.` and say that the chain wrote the JSON
of the published certificate byte for byte (sha256
`3594f19c4d01cf11fb930c5c61baeed399620acbc5b94096b16bcacb23997dd3`); the `.gz` file came out as the same
bytes too. It took 76 to 98 s on the Mac in five runs.

The Lean modules of the fourth result were written from this file by the two generators of this directory,
unchanged:

    python3 tools/gx/gxgen.py tools/certificate/gcert1-e8-r783.json.gz E8
    python3 tools/gx/gxrate.py B2Ge8 E8

`python3 tools/gx/regen_check_e8.py` runs both into a fresh directory and compares the 24 Lean modules and
`comparator/B2Ge8x.json` with the files of this repository, byte for byte.

Two limits of these checks:

- The checkers of this directory do not test which family the 120 ports are. `gx.check1` and the Python
  mirror of the Lean checks accept, with the same figure, a copy of this circuit carried to another family of
  120 ports. The test that the ports are the family described above is in `tools/e8/`.
- One field of the file, the frame number in each entry of the list of totals, is tested by the Python
  checkers only. No Lean check was found that reads it, and with that number changed in the first entry Lean
  builds the same theorem (VERIFY.md, section 10.5).

What this repository proves about the file does not depend on how it was made: the Lean kernel checks the
generated modules.
